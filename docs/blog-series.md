## 1. 系列定位

这不是“教程合集”，而是一个**问题驱动**的项目记录：

- 每个问题有现象、日志、假设、实验、根因、修复、验证；
- 每篇对应一个可运行的里程碑；
- 每篇底部链接仓库、commit、上一篇/下一篇；
- 不写“Day 1 接线、Day 2 点灯”的日记。

系列主线：

```text
基线审计 → ISO-TP → UDS/DTC → Bootloader → OTA → Linux 网关 → IIO/PIR 驱动 → 测试报告
```

## 4. 单篇模板

```text
标题：STM32 + i.MX6ULL CAN 诊断与 OTA（0X）：<具体问题>

1. 背景与目标（这段要解决什么）
2. 环境（板子、内核、工具链、接线）
3. 现象（日志/抓包/波形/截图）
4. 假设与实验（我怀疑什么，怎么验证）
5. 根因（真正的原因）
6. 修复（代码/配置/硬件改动）
7. 验证（命令、数据、前后对比）
8. 踩坑清单
9. 仓库/commit/下一篇
```

写作要求：

- 至少 1 张真实日志/截图，不要只放代码；
- 关键代码只贴 20–40 行，完整代码放仓库；
- 每个数字注明测试条件；
- 失败的过程也可以写，但结论要明确；
- 标题带系列编号，方便读者串联。

## 5. 第一篇《基线审计》提纲

### 标题

```text
STM32 + i.MX6ULL CAN 诊断与 OTA（01）：旧 CAN 项目基线审计
```

### 结构

1. **为什么要审计**
   - 旧项目“能跑”，但不知道哪些能复用；
   - 不审计就直接写 UDS，会在旧坑上再踩一遍。

2. **审计范围**
   - STM32 固件：CAN、AHT20、光照、PIR、USART；
   - i.MX6ULL：SocketCAN 收发；
   - 硬件：收发器、终端电阻、共地；
   - 文档：旧 README/博客。

3. **跑起来：先证明基线可用**
   - 串口日志；
   - `candump` 抓包；
   - `ip -details -statistics link show can0`；
   - 记录 commit。

4. **逐模块结论**
   - 复用：`bsp_can`、`aht20`、`light`、`pir`、`usart`；
   - 部分复用：SocketCAN 程序 → 重构成网关 `can_rx`；
   - 不直接复用：教程式 main、阻塞延时、无错误处理代码。

5. **发现的坑**
   - 错误帧没统计；
   - 没有版本号；
   - 失败没有错误码；
   - Flash 没有分区表；
   - 日志不可复现。

6. **基线冻结**
   - 打 `a-baseline` tag；
   - README 写清楚“已有什么/没有什么”；
   - 新功能从下一个 commit 开始。

7. **下一步**
   - 先加错误帧统计和版本号；
   - 再进 ISO-TP。

8. **仓库/commit**
   - 链接到本仓库；
   - 贴 `a-baseline` tag。
